# Сервис обратной связи

## Назначение

Приложение для сбора, обработки и управления отзывами и обращениями
пользователей. Консольная версия дополнена веб-интерфейсом на Django, который в ПР6 переведён на систему шаблонов Django, а в ПР7 получает
данные из реляционной базы SQLite с помощью SQL-запросов. Сервис позволяет
пользователям оставлять сообщения с обратной связью по различным категориям,
а администраторам — управлять этими сообщениями и давать на них ответы.

## Целевая аудитория

- Конечные пользователи: пользователи, желающие оставить отзыв или обращение.
- Администраторы: сотрудники поддержки, ответственные за обработку обратной
  связи.

## Предметная область

Сервис обратной связи относится к области управления клиентским опытом и
предоставляет структурированный способ сбора и обработки отзывов.

Основными объектами предметной области являются:

- пользователь;
- сообщение;
- ответ.

Пользователь может создавать сообщения, если у него есть на это право.
Каждому сообщению может быть дан ответ администратора — при этом сообщение
переходит в статус «закрыта». Ответ можно отменить: тогда он удаляется из
списка ответов.

## Используемые технологии

- Python 3;
- Django 5.2 — веб-фреймворк;
- Django Template Language (DTL) — шаблоны веб-страниц;
- HTML5 — разметка веб-страниц;
- CSS3 и Bootstrap 5.3 — оформление страниц (Bootstrap подключается через
  CDN, собственные стили — через static-файлы);
- JavaScript — небольшое клиентское поведение интерфейса;
- SQLite и SQL — реляционное хранение данных и запросы к ним;
- sqlite3 (стандартная библиотека Python) — работа с базой из Python;
- JSON — исходные данные и хранилище консольной версии;
- pytest — автоматизированные тесты;
- flake8 — проверка качества кода;
- mypy — статическая проверка типов.

## Основные сущности

### User — пользователь

Объект `User` представляет пользователя сервиса. Может быть обычным
пользователем или администратором.

Основные атрибуты:

- `id` — уникальный идентификатор пользователя;
- `name` — имя пользователя;
- `email` — адрес электронной почты;
- `role` — роль пользователя (`user` или `admin`).

Основные методы:

- `get_role_description()` — текстовое описание роли пользователя;
- `can_create_message()` — проверка права пользователя на создание сообщений;
- `__str__()` — строковое представление пользователя;
- `from_data()` — создание объекта `User` из набора данных (например, из
  JSON).

### Message — сообщение

Объект `Message` представляет сообщение обратной связи, оставленное
пользователем. Хранит ссылку на объект `User` — своего автора, а не только
его идентификатор.

Основные атрибуты:

- `id` — уникальный идентификатор сообщения;
- `author` — объект `User`, оставивший сообщение;
- `category` — категория сообщения;
- `text` — текст сообщения;
- `status` — статус обработки (`новая`, `в обработке`, `закрыта`);
- `created_at` — дата и время создания.

Основные методы:

- `get_status_text()` — текстовое описание статуса сообщения;
- `mark_closed()` — перевести сообщение в статус «закрыта»;
- `matches()` — проверить, содержит ли текст сообщения заданную подстроку;
- `__str__()` — строковое представление сообщения;
- `validate()` — статический метод проверки валидности текста и категории
  сообщения;
- `from_data()` — создание объекта `Message` из набора данных с
  восстановлением связи с объектом `User`.

### Response — ответ

Объект `Response` представляет ответ администратора на сообщение
пользователя. Хранит ссылку на объект `Message`, к которому относится ответ,
а не только его идентификатор.

Основные атрибуты:

- `id` — уникальный идентификатор ответа;
- `message` — объект `Message`, на который дан ответ;
- `text` — текст ответа;
- `created_at` — дата и время создания.

Основные методы:

- `__str__()` — строковое представление ответа;
- `from_data()` — создание объекта `Response` из набора данных с
  восстановлением связи с объектом `Message`.

## Взаимодействие объектов

При создании ответа объект `Response` связывается с объектом `Message`, а тот,
в свою очередь, хранит ссылку на своего автора — объект `User`

При создании ответа (`create_response()`) сообщение автоматически переводится
в статус «закрыта» вызовом его собственного метода `message.mark_closed()`.
Нельзя создать второй ответ на уже отвеченное сообщение — это проверяет
функция `is_message_answered()`.

## Основные операции

### Работа с пользователями

- добавление пользователя;
- поиск пользователя по имени;
- просмотр списка пользователей.

### Работа с сообщениями

- добавление сообщения (с проверкой прав автора и валидности текста);
- поиск сообщения по подстроке текста;
- фильтрация сообщений по статусу и категории;
- сортировка сообщений по дате;
- просмотр сообщений, на которые ещё не дан ответ (генератор);
- статистика по сообщениям (по статусам и категориям).

### Работа с ответами

- создание ответа на сообщение (сообщение при этом закрывается);
- просмотр ответов и ответов на конкретное сообщение;
- отмена ответа.

Все страницы, кроме главной, получают данные из базы SQLite SQL-запросами
(подробнее — в разделе «База данных»). Если сообщение или ответ с указанным
идентификатором не найден, страница возвращает код статуса 404
(`status=404 if ... is None else 200`). Для несуществующих адресов настроена
собственная страница 404 (`handler404` в `feedback_service/urls.py`, view
`page_not_found()`, шаблон `homepage/404.html`; видна при `DEBUG = False`).

Пользовательские сценарии веб-интерфейса:

1. просмотр списка сообщений (`/messages/`);
2. просмотр сообщения с автором и ответом (`/messages/<id>/`);
3. просмотр списка ответов и ответа с исходным сообщением (`/responses/…`);
4. поиск сообщений по категории, статусу, тексту и дате (`/messages/search/`);
5. сообщения без ответа (`/messages/unanswered/`);
6. статистика по статусам, категориям и авторам (`/messages/statistics/`).

Создание сообщений и ответов через веб-формы появится на следующих работах;
пока они добавляются в консольной версии.

## Хранение данных

В проекте два хранилища, которые связывает однократный перенос данных:

| Часть приложения | Источник данных |
|---|---|
| консольная версия (`main.py`, `storage.py`, `models/`) | JSON-файлы `data/users.json`, `data/messages.json`, `data/responses.json` |
| веб-версия (Django-представления) | база SQLite `data/feedback.sqlite` |

**Консольная версия** хранит данные в JSON: в файлах лежат списки словарей, а
связи сообщения с пользователем и ответа с сообщением заданы идентификаторами
(`user_id`, `message_id`). При загрузке `storage.py` преобразует JSON в объекты
`User`, `Message`, `Response`, при сохранении — обратно в словари.

**Веб-версия** читает базу SQLite. Данные в неё переносятся из JSON скриптом
`db/import_json.py`. Консольная версия по-прежнему пишет только в JSON
(данные сохраняются при выходе через пункт «0»), поэтому сообщения, добавленные
в консоли, появятся на сайте после повторного переноса:

```
python -m db.import_json --reset
```

Ключ `--reset` очищает таблицы и заново загружает данные из JSON
(правки, внесённые прямо в базу, при этом теряются). Без ключа скрипт
выполняет перенос только в пустую базу и иначе завершается с сообщением,
ничего не меняя.

## База данных

### Структура

База данных SQLite хранится в одном файле `data/feedback.sqlite`. Таблицы
созданы командами из `sql/schema.sql`.

Таблица `users` — пользователи:

| Поле | Тип | Назначение |
|---|---|---|
| `id` | INTEGER | идентификатор, первичный ключ |
| `name` | TEXT NOT NULL | имя пользователя |
| `email` | TEXT NOT NULL | электронная почта |
| `role` | TEXT NOT NULL | роль: `user` или `admin` (по умолчанию `user`) |

Таблица `messages` — сообщения:

| Поле | Тип | Назначение |
|---|---|---|
| `id` | INTEGER | идентификатор, первичный ключ |
| `user_id` | INTEGER NOT NULL | автор, внешний ключ → `users.id` |
| `category` | TEXT NOT NULL | категория сообщения |
| `text` | TEXT NOT NULL | текст сообщения |
| `status` | TEXT NOT NULL | статус: `новая`, `в обработке`, `закрыта` (по умолчанию `новая`) |
| `created_at` | TEXT NOT NULL | дата и время в формате `ГГГГ-ММ-ДД ЧЧ:ММ` |

Таблица `responses` — ответы:

| Поле | Тип | Назначение |
|---|---|---|
| `id` | INTEGER | идентификатор, первичный ключ |
| `message_id` | INTEGER NOT NULL UNIQUE | сообщение, внешний ключ → `messages.id` |
| `text` | TEXT NOT NULL | текст ответа |
| `created_at` | TEXT NOT NULL | дата и время ответа |

Связи: пользователь может написать несколько сообщений, каждое сообщение
принадлежит одному пользователю; на сообщение даётся не более одного ответа
(ограничение `UNIQUE` соответствует правилу из ПР3 — повторный ответ
запрещён). Поля, допускающие отсутствие значения (`NULL`), в таблицах не
предусмотрены: все данные обязательны. Дата хранится строкой, поэтому даты
можно сравнивать и сортировать средствами SQL. Допустимые значения роли и
статуса контролируются ограничениями `CHECK`.

### Файлы слоя базы данных

- `sql/schema.sql` — создание таблиц (`CREATE TABLE IF NOT EXISTS`, повторный
  запуск не вызывает ошибок);
- `sql/queries.sql` — SQL-запросы проекта с комментариями (22 запроса);
- `db/database.py` — подключение к базе: `get_connection()` включает проверку
  внешних ключей (`PRAGMA foreign_keys = ON`) и добавляет функцию
  `lower_u()` для поиска по русскому тексту без учёта регистра (встроенные
  `LIKE` и `lower()` SQLite понимают регистр только у латиницы);
  `create_schema()` выполняет `sql/schema.sql`;
- `db/import_json.py` — перенос данных из JSON в таблицы (`executemany()`,
  параметры `?`, порядок `users` → `messages` → `responses` из-за внешних
  ключей, `commit()` при успехе и `rollback()` при ошибке);
- `db/testing.py` — временная база для тестов;
- `data/feedback.sqlite` — файл базы данных.

### Создание базы и перенос данных

Одной командой (создаёт файл, таблицы и переносит данные):

```
python -m db.import_json
```

То же по шагам:

```
python -c "import sqlite3; sqlite3.connect('data/feedback.sqlite').close()"
python -c "import sqlite3; conn=sqlite3.connect('data/feedback.sqlite'); conn.executescript(open('sql/schema.sql', encoding='utf-8').read()); conn.commit(); conn.close()"
python -m db.import_json
```

Проверка: `sqlite3 data/feedback.sqlite ".tables"`,
`PRAGMA foreign_key_list(messages);`, `SELECT COUNT(*) FROM messages;`.

### SQL-запросы

В `sql/queries.sql` собраны запросы по видам; каждый проверен в SQLite CLI
(`sqlite3 data/feedback.sqlite < sql/queries.sql`) и автоматическим тестом:

- **выборка списков (`SELECT`)**: сообщения, пользователи, ответы, категории
  (`DISTINCT`), последние сообщения (`LIMIT` / `OFFSET`);
- **фильтрация (`WHERE`)**: по категории, по статусу, по подстроке (`LIKE`),
  по нескольким условиям (`AND`), по периоду (`BETWEEN`) и набору статусов
  (`IN`);
- **соединение таблиц (`JOIN`)**: сообщения с автором, ответы с сообщением и
  автором, сообщения без ответа (`LEFT JOIN … IS NULL`);
- **агрегатные функции**: `COUNT`, `MIN`, `MAX`, `AVG`, `COUNT(DISTINCT …)`;
- **группировка (`GROUP BY`, `HAVING`)**: сообщения по статусам, категориям,
  авторам (включая авторов без сообщений), авторы и категории с количеством
  сообщений выше порога.

### Получение данных в Django-представлениях

Представления `feedback/views.py` и `responses/views.py` подключаются к базе
через `get_connection()`, настраивают `conn.row_factory = sqlite3.Row`,
выполняют запрос, закрывают соединение и передают строки в шаблон через
`context`. Благодаря `sqlite3.Row` к полям результата можно обращаться по
именам (`{{ message.author_name }}`), а не по индексам. Значения всегда
передаются параметрами `?`: ни f-строки, ни конкатенация строк для подстановки
данных пользователя не используются, поэтому введённый текст не может
изменить сам запрос. Пример (страница сообщения):

```python
DETAIL_SQL = "SELECT ... FROM messages JOIN users ON ... WHERE messages.id = ?;"
message = conn.execute(DETAIL_SQL, [message_id]).fetchone()
```

В поиске пустое значение параметра отключает условие
(`(? = '' OR messages.category = ?)`), поэтому текст запроса остаётся
постоянным. Если в базе нет подходящих записей, шаблоны выводят сообщение
через `{% empty %}`.

## Шаблоны Django (ПР6)

HTML больше не формируется в Python: view-функции только загружают данные,
готовят контекст и вызывают `render(request, "шаблон.html", context)`.
Функция `page()` из ПР5 удалена.

### Базовый шаблон и наследование

`templates/base.html` содержит общую структуру страницы: подключение
Bootstrap и собственного CSS, логотип, навигацию, контейнер, подвал и
JavaScript. Дочерние шаблоны наследуют его через `{% extends "base.html" %}` и
переопределяют блоки `{% block title %}` и `{% block content %}`. Каталог
`templates/` подключён в `TEMPLATES["DIRS"]` в `settings.py`.

### Включаемые шаблоны (`{% include %}`)

- `templates/includes/navigation.html` — навигация (подключается в
  `base.html`);
- `feedback/includes/message_card.html` — карточка одного сообщения в списке;
- `feedback/includes/message_status.html` — бейдж статуса сообщения
  (`новая` / `в обработке` / `закрыта`), используется и в списке, и на
  странице сообщения.

### Контекст, циклы и условия

Передача данных через контекст, например для списка сообщений:

```python
context = {"messages_list": messages_list}
return render(request, "feedback/message_list.html", context)
```

В шаблонах используются `{% for %}` с `{% empty %}` (пустые списки
сообщений и ответов) и `{% if %}` / `{% elif %}` / `{% else %}` (статус
сообщения, наличие сообщения и ответа, отсутствующий объект).
Ключ контекста назван `messages_list`, а не `messages`, чтобы не пересекаться
с переменной `messages` встроенного context processor Django.

### Именованные URL и пространства имён

В `urls.py` приложений заданы `app_name` и имена маршрутов: `homepage:index`,
`feedback:list`, `feedback:detail`, `feedback:search`,
`feedback:unanswered`, `feedback:statistics`, `responses:list`,
`responses:detail`.
Ссылки в шаблонах формируются тегом `{% url %}`, например
`{% url 'feedback:detail' message.id %}`; жёстко заданных адресов нет.

### Фильтры шаблонов

- `{{ messages_list|length }}` — количество сообщений;
- `{{ message.author_name|default:"Автор не указан" }}` — значение по
  умолчанию;
- `{{ message.text|truncatechars:80 }}` — сокращение длинного текста в списке;
- `{{ message.text|linebreaksbr }}` — переносы строк в тексте сообщения.

Текст из `{{ ... }}` экранируется автоматически, поэтому HTML-теги в тексте
сообщений не выполняются. Дата создания хранится в базе строкой и выводится
без фильтра `date`.

### Статические файлы

Находятся в `homepage/static/homepage/` и подключаются через
`{% load static %}` и `{% static %}`:

- `css/style.css` — собственные стили (логотип, карточки сообщений, статусы);
- `js/main.js` — подстановка текущего года в подвал;
- `img/logo.png` — логотип сервиса.

## Структура Django-проекта

- `manage.py` — запуск команд Django;
- `feedback_service/` — пакет настроек проекта (`settings.py`, `urls.py` —
  корневая маршрутизация, `asgi.py`, `wsgi.py`);
- `templates/` — шаблоны уровня проекта: `base.html`,
  `includes/navigation.html`;
- `homepage/` — главная страница: `views.py` (`index()`, обработчик 404
  `page_not_found()`), `urls.py`, `templates/homepage/` (`index.html`,
  `404.html`), `static/homepage/` (CSS, JS, логотип);
- `feedback/` — приложение сообщений: `views.py` (`messages()`,
  `message_detail()`, `search()`, `unanswered()`, `statistics()`), `urls.py`,
  `templates/feedback/` (`message_list.html`, `message_detail.html`,
  `message_search.html`, `message_unanswered.html`, `statistics.html`,
  `includes/message_card.html`, `includes/message_status.html`);
- `responses/` — приложение ответов: `views.py` (`responses()`,
  `response_detail()`), `urls.py`, `templates/responses/`
  (`response_list.html`, `response_detail.html`);
- `db/` — слой базы данных SQLite (`database.py`, `import_json.py`);
- `sql/` — SQL-файлы (`schema.sql`, `queries.sql`);
- `data/` — JSON-файлы (консольная версия) и база `feedback.sqlite`;
- пользователи отдельного приложения не имеют: Django предоставляет
  встроенную модель `User`; класс `User` из `models/users.py` используется как
  часть предметной области.

Приложение сообщений названо `feedback`, а не `messages`, так как имя
`messages` уже занято встроенным `django.contrib.messages`. Файлы `models.py`
приложений пока пусты: Django-модели появятся на следующих работах.
Классы предметной области лежат в пакете `models/` в корне проекта.

## Назначение модулей

### `main.py`

Точка входа в приложение. Отвечает за:

- запуск приложения и главное меню;
- получение данных от пользователя;
- организацию пользовательских сценариев (добавление пользователя/сообщения,
  создание и отмена ответа и т. д.).

### `models/users.py`

Содержит класс `User` и функции работы с коллекцией пользователей:
`add_user()`, `find_user()`, `find_user_by_id()`, `show_users()`.

### `models/messages.py`

Содержит класс `Message` и функции работы с коллекцией сообщений:
`add_message()`, `find_messages()`, `filter_messages_by_status()`,
`filter_messages_by_category()`, `sort_messages_by_date()`,
`count_messages_by_field()`, `find_message_by_id()`, `show_messages()`.

### `models/responses.py`

Содержит класс `Response` и функции работы с коллекцией ответов:
`create_response()`, `cancel_response()`, `is_message_answered()`,
`get_responses_for_message()`, `iter_unanswered_messages()`,
`show_responses()`.

### `db/`

Слой базы данных SQLite: `database.py` (подключение), `import_json.py`
(перенос данных из JSON). Подробнее — в разделе «База данных».

### `storage.py`

Отвечает за загрузку и сохранение данных консольной версии в JSON.
Выполняет преобразование:

- JSON → объекты `User`, `Message`, `Response`;
- объекты `User`, `Message`, `Response` → JSON.

### `utils.py`

Содержит вспомогательные функции безопасного ввода:

- `input_int()` — ввод целого числа;
- `input_nonempty_str()` — ввод непустой строки;
- `input_choice()` — ввод значения из списка допустимых вариантов.

### `tests/`

Содержит автоматизированные тесты проекта: создание и поведение объектов
`User`, `Message` и `Response`, работу функций-коллекций и бизнес-правила
(валидация сообщений, запрет повторного ответа), а также слой базы данных
(`test_database.py`: схема, внешние ключи, ограничения, импорт из JSON,
проверка запросов из `sql/queries.sql`).

## Запуск приложения

Установка зависимостей (в виртуальном окружении):

```
python -m venv venv
source venv/bin/activate   # Windows: venv\Scripts\activate
pip install -r requirements.txt
python manage.py migrate
python -m db.import_json     # создать базу данных SQLite и перенести данные из JSON
```

Файл `data/feedback.sqlite` лежит в репозитории, поэтому последний шаг нужен
только при отсутствии базы или для её пересоздания (`--reset`).

Веб-версия (Django):

```
python manage.py runserver
```

После запуска открыть в браузере http://127.0.0.1:8000/

Консольная версия (сохранена):

```
python main.py
```

После запуска отображается главное меню.

## Тестирование

Для запуска автоматизированных тестов выполнить:

```
pytest
python manage.py test
```

`pytest` проверяет предметную область (ПР3), `manage.py test` — страницы
Django-приложений: используемые шаблоны, пространства имён URL, коды ответов
(в том числе 404), пустые списки, экранирование HTML, подключение
статических файлов, поиск, статистика и получение данных из SQLite.
Веб-тесты работают с временной базой данных, а не с `data/feedback.sqlite`.

## Проверка качества кода

```
flake8 . --extend-exclude=venv
```

Каталог `venv/` исключён из проверки в `.flake8`.

```
mypy .
```

## Текущее состояние и план развития

Реализовано:

- предметные классы `User`, `Message`, `Response`, консольный интерфейс,
  хранение данных консольной версии в JSON, тесты;
- Django-проект и три приложения (`homepage`, `feedback`, `responses`),
  маршрутизация двух уровней, именованные URL и пространства имён;
- веб-страницы на Django-шаблонах (базовый шаблон, наследование, `include`,
  контекст, циклы, условия, фильтры), собственные CSS, JavaScript и
  изображение, Bootstrap 5.3, собственная страница 404;
- **ПР7:** реляционная база SQLite (три таблицы, первичные и внешние ключи),
  `sql/schema.sql`, перенос данных из JSON (`db/import_json.py`), 22 SQL-запроса
  в `sql/queries.sql`, получение данных из SQLite в Django-представлениях
  (`sqlite3.Row`, параметризованные запросы), страницы списка и карточки
  сообщения, ответов, поиска, сообщений без ответа и статистики.

Django ORM, модели Django и формы пока не используются; база SQLite
обслуживается напрямую через `sqlite3` и существует отдельно от Django ORM.
